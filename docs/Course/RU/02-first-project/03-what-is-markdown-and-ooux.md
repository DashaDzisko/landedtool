

## Что такое файл Markdown (.md)

Файл Markdown — это простой текстовый файл с лёгким форматированием. Файл заканчивается на `.md`. Ты можешь открыть его в любом редакторе.

Markdown использует несколько простых значков:

- `#` для большого заголовка, `##` для поменьше
- `-` для пункта списка
- `` ` `` вокруг `code`, или три обратных апострофа для блока кода
- `**text**` для жирного

Вот крошечный пример:

```markdown
# My notes

## Colors
- Primary: salmon
- Background: charcoal

Use `bg-canvas` for the page background.
```

Вот и вся идея. Он остаётся читаемым как обычный текст, но инструменты могут превратить значки в красивое форматирование.

### Зачем мы его используем

Markdown читаем и **людьми**, и **ИИ-агентами** одновременно. Твой ИИ-агент читает `.md`-файлы так же, как читает код. Поэтому мы пишем спецификации проекта, правила и заметки по дизайну в Markdown, и агент следует им.

Посмотри на папку `docs/` в Landed. Почти всё там — `OOUX.md`, `design.md`, `project.md`, этот курс — это Markdown. Это общий язык между тобой и ИИ.

## Почему дизайн и OOUX идут раньше стройки

Вот ошибка, которую делает большинство: они открывают ИИ и говорят «собери мне трекер вакансий». У ИИ нет плана, поэтому он **угадывает**. Он угадывает данные — что вообще содержит заявка на работу. Он угадывает экраны. Каждая догадка своя, поэтому приложение выходит неряшливым, и ты его постоянно чинишь.

Решение — сначала определить важные вещи, записать их в Markdown и дать ИИ строить по этому плану.

### Начни с объектов

Прежде чем экраны или цвета, спроси: **какие реальные вещи есть в этом приложении?** Это твои объекты. Для Landed объекты такие:

- **Application** — одна вакансия, которую ты отслеживаешь. Это центр приложения.
- **Chat** — разговор с ИИ-агентом.
- **Account** — твой профиль и настройки.

Некоторые вещи поменьше живут *внутри* этих объектов и никогда не получают своей страницы. В Landed это: запись **Status**, человек-**Contact**, **Note**, файл **CV** и **Message** в чате.

### Порядок ORCA

Есть простой метод для этого — **OOUX** (Object-Oriented UX). Он проходит четыре шага по порядку, которые запоминаются как **ORCA**:

1. **O**bjects — какие реальные вещи есть (Application, Chat, Account)
2. **R**elationships — как они связаны (у Account много Applications; у Application много записей Status)
3. **C**alls to action — что можно делать (добавить заявку, изменить статус, отправить сообщение)
4. **A**ttributes — какие детали хранит каждый объект, в порядке приоритета

Последний шаг важен для интерфейса. Для Application в Landed атрибуты ранжируются так: **1) Status → 2) Role → 3) Company → 4) Date applied.** Поэтому каждая карточка заявки начинается с цветного бейджа статуса, затем роль, затем компания, затем дата. Самое заметное с первого взгляда идёт первым.

Всё это можно прочитать в `docs/OOUX.md`. Это было написано **до** того, как был построен хоть один экран.

### План и код согласованы

Вот в чём выгода. Поскольку модель объектов была написана первой, всё остальное с ней совпадает:

- База данных в `supabase/migrations/` имеет таблицы ровно под эти объекты — `applications`, `status_entries`, `notes`, `contacts`, `chats`, `chat_messages`.
- TypeScript-формы в `types/application.ts` описывают ту же Application, с теми же полями.
- Карточка заявки в интерфейсе показывает те же четыре атрибута в том же порядке.

Ничто не разъехалось, потому что ИИ строил по одному согласованному плану, а не угадывал три раза.

### Затем дизайн-система

Дизайн идёт раньше страниц по той же причине. Если ты не скажешь ИИ, какие цвета использовать, он выбирает случайные на каждом экране. Поэтому Landed сначала определяет свои цвета, шрифты и отступы как токены в `app/globals.css`. Тогда, когда ИИ строит страницу, он тянется к `bg-canvas` и `text-primary` вместо того, чтобы придумывать новый синий.

### Бриф, по которому строит ИИ

Собери это вместе — и у тебя есть твой бриф:

- **Документ OOUX** (`docs/OOUX.md`) — какие вещи есть и как они связаны
- **Документ дизайна / токены** (`app/globals.css`) — как они должны выглядеть

Когда оба записаны в Markdown, ИИ больше не угадывает. Он следует плану, который ты написал. Вот и вся идея «зачем раньше кода».

## Советы

- Запиши объекты, прежде чем просить хоть один экран. Десять минут OOUX экономят часы починки.
- Держи свои `.md`-документы короткими и актуальными. ИИ читает всё, что там есть, включая устаревшие куски.
- Когда ИИ строит что-то, что кажется не тем, проверь, действительно ли твоя модель объектов говорила то, что ты хотел. Часто чинить нужно документ, а не код.
