
## Почему нужно думать о безопасности

Когда ты строишь приложение с ИИ, код работает. Но это не значит, что он безопасен. ИИ пишет код, который делает своё дело, но он не всегда думает о безопасности. Кто-то может украсть данные твоих пользователей, использовать твои API-ключи или сломать твоё приложение.

Ты не эксперт по безопасности, и тебе не нужно им быть. Но стоит провести базовые проверки, прежде чем Landed выйдет в свет.

## Самые большие риски для вайбкод-приложений

### Открытые API-ключи

Твои API-ключи оказываются в коде или в публичном месте. В Landed нужно защищать `OPENAI_API_KEY`. Если кто-то его найдёт, он сможет сжечь твои кредиты OpenAI. Анонимный ключ Supabase — другое дело: он публичный по замыслу, и твоя безопасность идёт от RLS (об этом ниже).

### Нет валидации ввода

Пользователи могут ввести что угодно в твои формы. Без валидации кто-то может отправить вредные данные, которые сломают твоё приложение или твою базу данных.

### Отсутствующие проверки аутентификации

Страницы, которые должны быть приватными, доступны без входа. Кто-то открывает оболочку приложения или API-маршрут, просто вводя URL напрямую.

### SQL-инъекция

Кто-то вводит специальный код в поле формы. Если твоя база данных не обрабатывает его правильно, он может прочитать, изменить или удалить данные.

### Межсайтовый скриптинг (XSS)

Кто-то вставляет вредный JavaScript в поле формы (заметку, название компании). Когда это отрисовывается, скрипт запускается в чьём-то браузере.

## Промпты для проверки безопасности

Скопируй эти промпты и запусти их со своим ИИ-инструментом. Они проверяют твой проект на распространённые проблемы.

### Полный обзор безопасности

```
Просмотри весь мой проект на уязвимости безопасности. Проверь:
1. Открытые API-ключи или секреты в коде (не в .env файлах)
2. Отсутствующие проверки аутентификации на защищённых маршрутах
3. Отсутствующую валидацию ввода в формах
4. Риски SQL-инъекций в запросах к базе данных
5. Риски межсайтового скриптинга (XSS)
6. Проблемы с настройкой CORS
7. Отсутствие ограничения частоты запросов (rate limiting) на API-маршрутах

Для каждой найденной проблемы объясни, в чём риск и как это исправить.
```

### Проверка API-ключей

```
Найди во всём моём проекте любые API-ключи, токены или пароли, зашитые прямо в код.
Подтверди, что OPENAI_API_KEY читается только на сервере (без префикса NEXT_PUBLIC_,
используется только в маршрутах app/api/chats). Подтверди, что все секреты лежат в
.env.local и не закоммичены в Git. Также проверь, что .env.local есть в .gitignore.
```

### Проверка аутентификации

```
Просмотри все мои страницы и API-маршруты. Перечисли, какие требуют аутентификации,
а какие публичные. Landed использует вход по magic link. Есть ли маршруты, которые
должны быть защищены, но не защищены? Убедись, что каждый /api маршрут, который трогает
данные пользователя, сначала проверяет валидную сессию.
```

### Проверка форм и полей ввода

```
Просмотри все формы в моём проекте (форму magic-link, форму заявки, форму профиля,
поле ввода чата). Для каждой проверь:
1. Есть ли валидация ввода (длина, тип, обязательные поля)?
2. Очищаются ли данные ввода перед сохранением в базу данных?
3. Может ли кто-то отправить вредный HTML или JavaScript через форму?
4. Есть ли ограничение частоты запросов (rate limiting) против спама?

Исправь все найденные проблемы.
```

### Проверка безопасности базы данных

Это самая важная проверка для Landed. Приложение работает на Supabase, и безопасность данных каждого пользователя зависит от того, правильно ли настроен Row Level Security.

```
Просмотри настройку Supabase в supabase/migrations/0002_rls.sql и все запросы в
lib/db. Подтверди:
1. Row Level Security включён на КАЖДОЙ таблице (profiles, applications,
   status_entries, notes, contacts, chats, chat_messages).
2. Пользователи могут получить доступ только к своим строкам. Родительские таблицы
   ограничены через auth.uid(); дочерние таблицы (status_entries, notes, contacts,
   chat_messages) наследуют владельца от своей родительской заявки или чата.
3. Нет запросов, уязвимых для SQL-инъекций.
4. Ключ service-role Supabase, если он где-то используется, только на сервере и
   никогда не попадает в браузер.
```

В Landed это уже настроено правильно в `supabase/migrations/0002_rls.sql`: RLS включён для всех семи таблиц, доступ только к своим строкам через `auth.uid()`, а дочерние таблицы проверяют свою родительскую. Используй этот промпт, чтобы подтвердить, что ничего не сбилось после твоих изменений.

## После проверок

1. Исправь проблемы, которые нашёл ИИ. Начни с самых серьёзных (открытые ключи, отсутствующая аутентификация, пробелы в RLS).
2. Если ключ когда-либо утёк, смени его. Сгенерируй новый `OPENAI_API_KEY` в панели OpenAI и обнови `.env.local`. Старый остаётся опасным, пока ты этого не сделаешь.
3. Добавь правила безопасности в свой claude.md, чтобы ИИ не делал этих ошибок снова:

```markdown
## Security rules
- Never hardcode API keys. Always use environment variables.
- OPENAI_API_KEY is server-only. Never add a NEXT_PUBLIC_ prefix to it and never
  import it into a client component.
- All /api routes must check for a valid Supabase session before doing anything.
- Enable Supabase RLS on every new table, own-rows-only via auth.uid().
- All form inputs must be validated and sanitized before saving.
```

4. Запускай эти проверки снова перед каждым деплоем. Сделай это привычкой.

## Советы

- Делай проверки безопасности прежде, чем поделишься приложением с реальными пользователями. Не после.
- С Supabase безопасность идёт от RLS, а не от сокрытия анонимного ключа. Анонимный ключ публичный; именно RLS не даёт пользователю A читать заявки пользователя B.
- `OPENAI_API_KEY` никогда не должен покидать сервер. Он живёт только в маршрутах `app/api/chats`.
- Никогда не доверяй данным от пользователей. Всегда валидируй и очищай их, даже если они пришли из формы, которую ты сам сделал.
- Запускай проверки безопасности после добавления новых фич. Новый код значит новые возможные проблемы.
